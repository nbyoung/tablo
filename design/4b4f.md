# Design 4b4f: Conformance

The conformance test runs the `tablo` command over every entry of the tableaux conformance corpus and compares what the command emits with the entry's `expected.yaml`: the findings by rule and location, then each derived fact the file states. Four choices shape it. `tablo` carries a copy of the corpus at one locked tableaux commit, embedded into a test helper, so `go test ./...` needs no network and no sibling checkout. The test drives the built command as a black box, as every front end does, and reads only its JSON. It turns the command's output into a document of `expected.yaml`'s own shape and compares the two generically, so the assumptions about the command's data sit in one table. A list of known failures keeps the trunk green while an entry waits for a fix, and fails when an item outlives its reason.

The task has no prototype: the mockup and function gates do not apply to it. A trial outside the repository stands in for one; [Tests](#tests) says what it shows. The drafts under [`4b4f/`](4b4f/) fix the shapes.

## The model

### Two packages

| Path                    | Package       | Holds                                                                                              |
|-------------------------|---------------|----------------------------------------------------------------------------------------------------|
| `internal/corpustest/`  | `corpustest`  | The copy of the corpus, its lock, its build, the entries, the labels and the rule list. A test in any package of the module imports it. |
| `internal/conformance/` | `conformance` | The conformance test itself, in `_test.go` files only, plus `doc.go`, `known.yaml` and its goldens. |

The split serves the other tasks. Every prototype test today reads the corpus at an absolute path on one machine (`/home/nbyoung/Projects/Tableaux/tableaux/corpus/build/…`) and skips anywhere else, so CI checks none of them against the corpus. The validator, the derivation, the audit and the three view tasks test against corpus entries before the command exists; `corpustest` gives them the entries, and it needs nothing of the command, so it lands first ([Implementation notes](#implementation-notes)). No package outside tests imports it, so it adds nothing to the `tablo` binary (T5).

### The corpus at a fixed version

`internal/corpustest/testdata/corpus/` holds a copy of the tableaux repository's `corpus/` directory at one commit: `entries/`, `base/`, `build.sh`, `lib.sh`, `RULES.md`, `README.md` and `check.py`, 756 files and 386 kB. `corpus.lock.yaml` beside it names the repository, the commit, the commit the tag `corpus/tooling` names at that time, and a digest of the copy. This is the form `schemas/` already takes: a copy and the commit it comes from. It makes no Git link, so `tablo` stays a submodule of the umbrella with no cycle, and a clone of `tablo` alone holds all a test run needs.

`corpus.sh` maintains the copy. `refresh <tableaux checkout> [<commit>]` replaces the copy from a local checkout with `git archive` and rewrites the lock; a contributor runs it, reads the diff and commits the copy and the lock in one commit. `fetch <directory>` clones the locked repository at the locked commit with its submodules, points the clone's own tag `corpus/tooling` at the locked tag commit, and fails unless the clone's `corpus/` equals the copy; only CI runs it. `digest` prints the digest: the SHA-256 of the lines `<sha256 of the file>  ./<path>`, one per file, sorted bytewise by path. `testdata/.gitattributes` holds `* -text`, so no checkout rewrites a line ending under the copy.

`corpustest` embeds the copy (`//go:embed all:testdata/corpus`; `all:` keeps the `.tableaux` directories) and writes it into a work directory before it builds, because `build.sh` builds only into `build/` beside itself and the repository tree stays clean.

The environment variable `TABLO_CORPUS` names another corpus directory in place of the copy: the umbrella's working `corpus/`, or the clone that `fetch` makes. `corpustest` then copies `entries/`, `base/`, `build.sh`, `lib.sh` and `RULES.md` from there into the work directory and builds as before; it never writes into the directory named.

### Building the entries

`sh build.sh <entry>` in the work directory builds one entry in about 0.2 s; all 98 built entries take under 4 s. `corpustest` builds an entry on first use and once per test process. It runs the script with a closed environment, so no host setting reaches a commit: `PATH` from the host, `HOME` set to the work directory, `GIT_CONFIG_GLOBAL` set to the null device, `GIT_CONFIG_NOSYSTEM=1`, `TZ=UTC`, `LC_ALL=C`. The corpus fixes every identity, date and message, so the hashes repeat; no test compares a hash with a literal all the same, since every comparison goes through the labels files the build writes.

A build needs `git` and `sh` on the path. Where either is absent, `Open` skips the test and says which is missing; when the environment holds `CI`, it fails the test, so CI never passes by skipping.

The command reads an entry whose `expected.yaml` has `source` in place: its repository is `source.repository` resolved against the entry's directory in the corpus named, and its ref is `source.ref`. In the embedded copy that path leads nowhere, so `Entry` skips a read-in-place entry unless the environment holds `TABLO_CORPUS`.

```go
package corpustest

// Main runs a package's tests and then removes the work directory that
// Open made, unless the environment holds TABLO_KEEP; it returns the exit code. A package
// that uses the corpus calls it: func TestMain(m *testing.M) { os.Exit(corpustest.Main(m)) }.
func Main(m *testing.M) int

// Corpus is the corpus of one test process: the embedded copy, or the
// directory TABLO_CORPUS names, written into a work directory.
type Corpus struct {
	Origin   string // "testdata/corpus", or the value of TABLO_CORPUS
	Vendored bool   // true for the embedded copy
	Work     string // the work directory: entries/, base/, build.sh, lib.sh, RULES.md, build/
}

// Open returns the process's corpus and makes the work directory on first
// use. It skips tb when git or sh is absent, and fails tb instead under CI.
func Open(tb testing.TB) *Corpus

// Names lists the entries, sorted.
func (c *Corpus) Names() []string

// Entry reads an entry's expected.yaml and builds its repository on first
// use. It skips tb for a read-in-place entry of the embedded copy.
func (c *Corpus) Entry(tb testing.TB, name string) *Entry

// Rules reads the rule tables of RULES.md, in file order.
func (c *Corpus) Rules(tb testing.TB) []Rule

// Env is the closed environment for git and for the command under test.
func (c *Corpus) Env() []string

// Entry is one corpus entry, ready to read.
type Entry struct {
	Name     string
	Expected *yaml.Node        // the mapping at the root of expected.yaml, with line numbers
	Language string            // the language field
	Valid    bool              // the valid field
	Repo     string            // the repository to read: build/<name>, or the source repository
	Ref      string            // the ref in view: ref, source.ref, or main
	Trunk    string            // the branch the caller names; empty unless trunk is { caller: <branch> }
	Replace  map[string]string // absolute URL to built repository, from the replace field
	InPlace  bool              // the entry has source
}

// Hash resolves a label through the entry's labels file and then through
// the labels files of its subprojects (build/<name>.*.labels.txt). Forty
// lowercase hexadecimal digits resolve to themselves.
func (e *Entry) Hash(label string) (hash string, ok bool)

// Label is the reverse of Hash, for messages; empty when no label names the hash.
func (e *Entry) Label(hash string) string

// Rule is one row of a rule table in RULES.md.
type Rule struct {
	ID       string   // "P1" … "H6"
	Severity string   // error, warning or information
	Entries  []string // the entries the row names
}

// Digest computes the digest of the embedded copy, as corpus.sh digest does.
func Digest() string

// Lock reads corpus.lock.yaml, embedded beside the copy.
func Lock() (repository, commit, tooling, digest string)
```

`Rules` takes each table row of the form `| <id> | <severity> | … | <entries> |` whose first cell matches `^[A-Z][0-9]+$`, as `check.py` does.

### One entry, one run

`TestCorpus` in `internal/conformance` runs one parallel subtest per entry, `TestCorpus/<entry>`. `TestMain` builds the command once (`go build -o <work>/tablo ../../cmd/tablo`), or takes the binary the environment variable `TABLO_BIN` names, and asks it for `version --json` (A7). Every call uses `Corpus.Env()` plus `GIT_AUTHOR_EMAIL` and `GIT_COMMITTER_EMAIL` set to `observer@example.org`, so the viewer holds no role in any entry, and a timeout of 30 s. The global options precede the command in this order:

```
tablo -C <Repo> --ref <ref> [--trunk <Trunk>] [--replace <url>=<dir>]… --json <command> [args]
```

| Step | Call                                                    | Compares                                                            |
|------|---------------------------------------------------------|---------------------------------------------------------------------|
| 0    | none                                                    | Skips the entry when the major number of `language` differs from the command's |
| 1    | `validate`                                              | `valid` with the exit code, 0 for true and 1 for false; `findings` with `diagnostics` |
| 2    | `view task --task <id> --level provenance`, per task    | Every fact under `tasks.<id>` but `events`; from the root, `owner`, `root`, `count`, `order` |
| 3    | `view history --task <id> --level provenance`, per task that states `events` | `tasks.<id>.events`                           |
| 4    | Steps 2 and 3 with `--ref <branch>`, per key of `refs`  | `refs.<branch>.commit` with the envelope's `ref.commit`; `refs.<branch>.tasks` as `tasks` |

Steps 2 to 4 run only when the file states a fact there. For `root`, `count` and `order` the test climbs `parent` from the stated root, or from the first task the file names, to the task with no parent, then walks `children` from it in the order given. An exit code of 2 or 3, a timeout, output that is not one JSON envelope, or a `schema` other than `tablo/1` is a mismatch of its own at the path `command`, with the first line of standard error.

### The observed document

`observe` turns the calls of one entry into a `map[string]any` shaped as `expected.yaml`; `compare` then walks the expected document and never looks at an envelope. The right-hand column is the only place that knows the command's data. Its paths come from the keys prototypes 493e and 8ed1 emit (A8, A9); when the implemented command names a value otherwise, the implementation changes that cell of the table in `observe_test.go` and nothing else.

| Fact in `expected.yaml`                 | Call      | Value in `data` (A8, A9), or in the envelope                                          |
|-----------------------------------------|-----------|----------------------------------------------------------------------------------------|
| `findings[]`                            | validate  | `diagnostics[]`: `code` as `rule`, `severity`, `path` as `file`, `task`, `gate`, `commit`, `trailer` (A3) |
| `owner`                                 | view task | `glance.assignee` of the root                                                          |
| `tasks.<id>.parent`                     | view task | `glance.parent.id`                                                                     |
| `.authorities`                          | view task | `detail.authorities`                                                                   |
| `.authorisation.state`, `.commit`, `.by` | view task | `provenance.authorisation.state`; `.commit.hash`; `.commit.author` or `.commit.committer`, as `.by` selects |
| `.junctions.default`                    | view task | `{ kind: plain, contributor: <glance.assignee> }`                                      |
| `.junctions.<gate>`                     | view task | The item of `detail.junctions` with that `gate`: `kind`, `contributor`, `model`, `reviewer`, `references`, `subproject` |
| `.junctions.<gate>.source`              | view task | The task ids among the values of `provenance.junction_sources[gate].sources`           |
| `.applicable`                           | view task | The `gate` of each item of `detail.junctions` whose `kind` is not `not_applicable`      |
| `.requires[]`                           | view task | `detail.requires[]`: `id` or `subproject`, `from`, `to`, `met`, `due`, `condition`       |
| `.reviews[]`                            | view task | `provenance.reviews[]`: `gate`, `reviewer`, `commit`                                    |
| `.subproject`                           | view task | `glance.status.snapshot`: `url`, `pin`, `task`                                          |
| `.status`                               | view task | `glance.status`: `gate`, `state`, `reason`, `note`, `date`, `recorder`, `commit`, `derived`, `from` |
| `.events[]`                             | view history | The items of `events[]` whose `task` is the id                                       |

### Comparison

A **fact** is one comparison, and the unit every count uses. The rules, complete:

1. **Scalars.** A string, a boolean or an integer compares for equality. A date compares as the ten characters `YYYY-MM-DD`: the node's text on the expected side, the first ten characters on the observed side. An id compares as the node's text, quoted or not.
2. **Labels.** Under the keys `commit`, `old`, `new` and `pin`, the expected value is a label, and `Entry.Hash` resolves it; the observed value is a full hash (A10). A label no file holds fails the subtest at once with the prefix `corpus:`, since the corpus is wrong and not the command.
3. **Absence.** Observed absent, `null`, `""` and `[]` are one value, *absent*. Expected `null` and `[]` equal it. Expected `false` does not.
4. **Maps compare by the keys the file states.** The command may state more, as corpus/README.md allows. Each stated scalar is one fact.
5. **A list of scalars is one fact and compares whole and in order**: `order`, `authorities`, `applicable`. `source` compares as a set, and a single string stands for a set of one.
6. **`requires` and `reviews` compare as sets of items**, keyed by `id` or by `subproject.url` with `subproject.id`, and by `gate`. The length is one fact; each stated key of each item is one fact.
7. **`events` compares in order.** The length is one fact. Within an item each of the keys `date`, `commit`, `by`, `task`, `event`, `gate`, `state`, `reason`, `note`, `url`, `old`, `new`, `subproject` is one fact, and a key the file leaves out must be absent. Any other observed key passes.
8. **`findings` compare as a multiset.** Each expected finding takes one observed finding not yet taken that agrees on `rule`, `severity` and each of `task`, `file`, `gate`, `commit`, `trailer` it states; the expected findings match in the order of most keys first. `message` never compares. Each expected finding is one fact. An observed finding left over is a mismatch and no fact, so a valid entry with `findings: []` fails on any diagnostic at all.
9. **`undecided`.** A map that holds the key `undecided` compares nothing and counts one undecided fact under its finding id (`F7` today).
10. **Inputs compare nothing**: `entry`, `language`, `trunk`, `ref`, `source`, `replace`. `Corpus.Entry` checks that `entry` equals the directory name.

The subtest lists mismatches in the order of `expected.yaml`'s lines, then the unexpected findings sorted by rule, file and task. Runs are deterministic: entries sort by name, and nothing in the output depends on time or on the work directory.

### How a failure reads

[`4b4f/failure.txt`](4b4f/failure.txt) is the golden. One header names the entry, the ref and the counts; each mismatch gives the path, what the file wants with its line in `expected.yaml` (and the label beside a hash), and what the command gives with the call that supplies it; the last line is the command that reruns the one entry and keeps the work directory. When the environment holds `TABLO_KEEP`, `Main` leaves the work directory and prints its path, and each `got` line shows the full command line.

### Known failures

[`known.yaml`](4b4f/known.yaml) lists entries the test expects to fail, each with a reason and the task that owes the fix. A listed entry still runs. When it fails, its subtest logs the mismatches and skips. When it passes, or when the list names no entry of the corpus, the subtest fails and says to remove the item. A listed entry that skips, as `tableaux-tooling` does in the embedded copy, stays listed. The list holds whole entries only; `undecided` is the corpus's own means for one fact.

The implementation fills the list by rule, with no judgement: each entry that fails on the first full run goes in, its `reason` the first mismatch line, its `owes` chosen by that mismatch's path: `findings` with a rule P, G, T, R, J or S owes `8118`; `findings` with a rule H owes `dada`; `events` owes `8ed1`; any other fact owes `27a3`; `command` owes `4ed9`. The hand-off note lists the items, and the owner moves an item to `fcec` and gives it a `finding` where the corpus is wrong.

### Coverage of the rules

`TestRules` checks, with no command: every rule in RULES.md has at least one finding in some `expected.yaml`; every entry a rule row names exists; every `rule` in an `expected.yaml` is in RULES.md; and its `severity` there equals the row's.

`TestCorpus` gathers each subtest's result, and a final step writes the report in the form of [`4b4f/report.md`](4b4f/report.md): per rule, the findings stated, matched, missing and unexpected over the entries that ran, with the result `confirmed` (stated and all matched, none unexpected), `failing`, `not run` (every entry that states it skipped) or `no entry`; an observed `code` that RULES.md lacks counts under "Findings outside the rules"; per fact kind, the facts stated, agreeing, differing and undecided; and the entries that do not pass. The kind of a fact is its key under `tasks.<id>`, or `project` for `owner`, `root`, `count` and `order`, or `refs`, `valid`, `findings`. The summary lines of the report go to the test log on every run; the whole report goes to the file `TABLO_REPORT` names, when it names one.

| Run                                   | Network | Corpus                          | Entries                                   |

| The umbrella, for `fcec`'s unit gate  | none    | The umbrella's `corpus/`        | All 99, at the working tree: `cd subprojects/tablo && TABLO_CORPUS=$PWD/../../corpus go test -count=1 ./internal/conformance` |

`go test ./...` needs the Go toolchain it runs under, `git`, `sh`, and the modules already in the module cache.

### Errors

The test has no exit codes of its own beyond `go test`'s. It tells three failures apart by prefix: `corpus:` for a corpus it cannot use (a build that fails, an unreadable `expected.yaml`, a label with no hash); `command:` for a command that does not answer (A1, A2); and the mismatch block for a command that answers otherwise than the file states. Only the third may enter `known.yaml`.

## Conformance to the texts

The design follows corpus/README.md, "How a tool consumes the corpus", sentence by sentence, with three departures. It builds in a work directory and not in `corpus/build`. It reads the `tableaux-tooling` entry only where the tableaux repository is at hand. It compares findings exactly (rule 8), where the text says only "by rule id and location": README.md gives an invalid entry "the finding, or the findings when one deviation trips two rules", so the list is complete by intent.

The task's description says the test compares "the diagnostics, findings and views". The corpus states facts, and VIEWS.md, "Data", says each view draws on those facts; it states no expected output of a view. This test therefore proves the facts under the task view and the history view, and proves nothing of the other eight views: the queue's order, the blockage tree, the tableau window and folds, and the three levels stay with the view tasks' own tests against the mockups (C8).

Of the known open points, two touch this task. The roll-up that takes the earliest gate among children holds `tablo`'s root at `defined` for as long as this task, exempt from mockup and function, stands at `defined`; and the corpus has no entry for a parent with such a child, so a change of that rule has no expectation to meet (C8). "A commit at a junction" stays undefined in the method; the entries `model-mismatch`, `model-trailer-missing` and `junction-kinds` fix it by example only, and the test holds the audit to those examples. The test passes no person and no window, so the `--for` or `--person` question does not bind it.

## Decisions at review

The owner decided each question this design raised on 2026-10-06, together with the cross-design rulings of that review; a decision the review did not reach stands as the design states it, accepted with the design.

1. **A copy at a locked commit.** Accepted with the design, as stated: `tablo` holds the corpus as files, embedded into `internal/corpustest`, with `corpus.lock.yaml` and `corpus.sh`. The alternative makes the tableaux repository a Go module that `go.mod` requires at a pseudo-version: no copy in `tablo`, at the price of Go files in the language repository and a module fetch before the first test run. Binds `fcec`. The lock's commit comes after the umbrella's review commits of 2026-10-06, which add rules L1 to L4 (4f60 decision 3) and move the tag `corpus/tooling`.
2. **The command as a black box.** Accepted with the design, as stated: the test builds `cmd/tablo` and reads its JSON. The command's form is one subcommand per view, `tablo tableau --json` and the like, as the owner ruled for 4ed9 decision 3; this design's references to `tablo view` read so. The alternative calls the library in process, which is faster and leaves the command's parsing, envelope and exit codes unproven.
3. **Findings compare exactly, from `validate` alone** (rule 8, A3). Accepted with the design, as stated: a diagnostic the entry does not state fails it, and `validate` reports the history rules too. The alternative lets extra findings pass and takes the H rules from `audit`. Binds `4ed9`, `8118`, `dada`.
4. **A project that is missing is a finding, not a failure to read** (A4). Decided by the owner on 2026-10-06, confirming all three designs: exit 1 with a P1, P2 or G1 diagnostic. The review note that 4f60 exited 3 was mistaken; 4f60's `Load` returns `Exists` false and no error, and the exit 3 belonged to the prototype. The project is the nearest `.tableaux` at or above `-C` (4f60 decision 7), so P1 fires only when none is there up to the root. Binds `4ed9`, `4f60` and tabloio's `1422` (its A4).
5. **`--trunk` and `--replace` join the public vocabulary** (A5, A6). Accepted with the design, as stated, the names prototype 27a3 and the corpus's `replace` field already use. The alternative for the mapping is Git's `url.<base>.insteadOf` with no option of `tablo`'s own. Binds `4ed9`, `4f60` and every front end that passes options through.
6. **A cross-project requirement on `fcec` in `4b4f`'s task file**, with the lock's commit. Decided by the owner on 2026-10-06: yes, so the plan states what the lock states, and `TestVendoredCopy` also checks that the two commits agree. The price: `tablo` then validates its own plan only with `--replace` or the network. The entry lands with the implementation, once the lock names its commit; until then the design's plan paragraph carries it, as README.md now allows for a requirement whose originating commit does not yet exist. The alternative left the link to the umbrella's `77b2`.
7. **Known failures, and the unit gate's rule.** Accepted with the design, as stated: `known.yaml` keeps the trunk green; the unit gate passes only when every item left cites a corpus finding the owner accepted. The alternative has no list, and one failing entry holds every merge.
8. **The CI job `corpus` clones the tableaux repository on every push** (A13). Accepted with the design, as stated. The alternative runs it on a schedule and on a change under `internal/`, and a stale copy shows later.
9. **`corpustest` lands before `4ed9`**, as step 1. Accepted with the design, as stated, for the validator, the derivation, the audit and the views to test against. The alternative leaves each to its prototype's absolute path until this task's implementation.
10. **The stale entry `tableaux-tooling`.** Decided by the owner on 2026-10-06, on this design's report: the tag `corpus/tooling` moves to the umbrella commit that raised the language to 0.3.1, so the entry's `language` is true at the tag it names; `check.py` learns to read an in-place entry's `version.yaml` at its ref; and the full re-verification of the entry's facts against the plan as it stands is this task's, since only a real tool reads the entry.
