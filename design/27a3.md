# Design 27a3: Derivation

The Derivation gives every fact a view shows that no file states: each junction resolved through the ancestors with the supplier of every field, each requirement's condition, each task's authorisation, each status's date and recorder, each review, each parent's roll-up, each task's events, and each recursive junction's status from the subproject at its pin. It is the one place in tablo that reads history, and the one owner of every derived fact: the Validator, the Audit and the three view tasks ask it and derive nothing. Six choices shape it, five of them decisions for the owner (D*n* is decision *n* under [Decisions at review](#decisions-at-review)). One `git log` per project reads the history, and the Derivation is a pure function of the model and that pass, which amends 4ed9's A4. A fact about a commit reads the files as they stand at that commit (D2). The source is on the trunk when its commit is on the trunk's first-parent line, and a linked repository takes its trunk from the remote-tracking branch (D4, D5). The fields above a not-applicable entry do not pass to a descendant that states its own (D1, which settles F7). The outgoing owner accepts a hand-over of the root (D3). The Derivation refuses only a project whose version, gating or tree it cannot read, so an invalid status never blanks a view (D6).

### The pass

Prototype 27a3 runs one `git` process per lookup and prototype 8ed1 one `git log` per range. The design keeps 8ed1's single pass and gives it to every reader of history. `Reader.Read` runs three processes per project of a load: the home project and each project a link reaches, in a submodule's store, in a clone a URL maps to, or in a directory of the same repository.

```
git for-each-ref --format='%(refname)%00%(objectname)%00%(symref)' refs/heads refs/remotes
git -c log.showSignature=false log --date-order --date=raw --diff-merges=first-parent --raw --no-abbrev
    --no-renames --no-color -z --full-history --sparse
    --format='%x01%H%x00%P%x00%an%x00%ae%x00%ad%x00%cn%x00%ce%x00%s%x00%(trailers:only,unfold)%x00'
    --end-of-options <source> <trunk tip> [<extra>…] -- <dir>/.tableaux <submodule path>…
git cat-file --batch          # every blob the pass names under <dir>/.tableaux
```

- **The trunk comes first.** The ref listing resolves the trunk as README.md#project orders it: `trunk` in the `version.yaml` in view; else the target of `refs/remotes/origin/HEAD`; else, for the home project alone, the branch the caller names; else none. The name resolves against `refs/heads/<name>`, then `refs/remotes/origin/<name>`, then the other remotes in byte order. In a linked repository the remote-tracking branch comes first (D5). A name no ref carries leaves the trunk undetermined, with the name kept for the message.
- **The walk** starts at the source commit, `Location.Commit`, and at the trunk's tip, since authorisation reads the trunk whatever the ref. `--full-history --sparse` keeps every commit, so a commit that carries a trailer and changes no file stays in the pass; the paths bound only what `--raw` prints. `--diff-merges=first-parent` gives each merge its changes against its first parent, which the deciding commit of a task needs. `--date-order` is the order "newest" means below: no parent before its child, and commit time otherwise.
- **Each commit keeps** its id and parents in full, the author's and the committer's name and email as committed, the author time and zone, the subject, the trailer block as Git parses it, and each watched path it changes with the object id on both sides. The pass adds its place in the order, whether the source reaches it, and its place on the trunk's first-parent line. A view's commit fact is this record.
- **The blobs** give the past. `Log.Object` returns the object at a path as any commit of the pass holds it, by applying each commit's changes to its first parent's table; `Log.Project` composes the project as its files stand at that commit, and parses each blob once however many commits share it. A merge changes a path only when its object differs from every parent's (`Log.Changed`), so a clean merge makes no event and a merge that writes its own reading does.
- **The memo.** A pass is a function of the repository, the directory, the tips and the paths, so the `Reader` keeps the last 64. A reload after an edit under `.tableaux` runs the ref listing alone for each project. `Read` takes further commits to walk, for a range that starts off the source's history (A4).
- **No history.** A load of a tree, or on an unborn branch, has no commit; `Set.Of` returns nil and every fact of the history is undetermined with `NoHistory`. `Log.Shallow` says the clone is shallow, where a pass may end before the history does.

**The cost**, measured on this host alone (WSL2, Git 2.47.3) on the Tableaux tooling plan: 37 tasks, 145 commits, four submodules of 75 to 96 commits.

| Step                                                                                  | Cost      |
|---------------------------------------------------------------------------------------|-----------|
| The ref listing, one repository                                                       | 2.3 ms    |
| The pass over the umbrella's 145 commits, bounded to `.tableaux` and four pins        | 19 ms     |
| The same pass with no path, as design 4ed9 measures it                                | 62 ms     |
| The batch of the 118 blobs that pass names                                            | 5.8 ms    |
| The pass over one subproject (tablo, 79 commits)                                      | 5.5 ms    |
| All five projects, fifteen processes, nothing remembered (the trial)                  | 74 to 81 ms |
| Every fact of the 37 tasks, 249 events among them, from the passes (the trial)        | 13 ms     |

So a first load costs about 90 ms beyond the Loader's, where 4ed9 estimates 36 ms for one pass and counts no subproject. A reload that moves no commit costs five ref listings, about 12 ms by the unit costs; T5 measures it. The passes run one after another; the integrate gate's benchmark decides whether they run together.

### The rules every fact shares

1. **Undetermined is a value.** A fact the files or the history cannot give carries a `Why` and its zero value; no method fails and none panics. The table below names the reason for each fact.
2. **The files in view state the plan; the files at a commit judge the commit** (D2). The authorities of a deciding commit, the reviewer a `Reviewed:` commit must be, the junction a status commit is at, the model that junction states and the language version all read `Log.Project` at that commit. README.md states this for the authorities and for the version; the design extends it to the other three, so that naming a new reviewer does not undo the reviews of the old one.
3. **Newest** is first in the pass among the commits the source reaches; **oldest** is last.
4. **A subproject's facts are its own.** `Facts.Sub` gives the `Facts` of the project a link leads to, derived by the same code from its own pass at the commit the link fixes. Two statuses that read each other through two directories of one repository are undetermined with `Cycle`.
5. **The working tree.** The files come from disk and the history from `HEAD`. A file that is not the source commit's sets `Uncommitted` on the task's authorisation or status; the deciding commit, date and recorder stay those of the history, and a view says which it shows. Files compare by their content as YAML, so a comment changes nothing.

corpus/RULES.md#derived-facts-not-rules names these as the facts a conforming tool agrees on. The throwaway trial of this design agrees with every one of the 1 939 facts that 22 valid entries state ([Tests](#tests)).

**1. The resolved junction.** `Junction(id, gate)` walks the task's own entry and then its ancestors' entries, nearest first.

- The task's own recursive entry resolves at once: a recursive junction takes nothing from an ancestor and gives nothing to a descendant.
- A plain entry supplies, field by field, what no nearer entry supplies: the reviewer; the references, whole; and the contributor with the model as one pair, so a child that states a person under a parent's agent takes no model ([`27a3/cases.md`](27a3/cases.md), J1).
- A not-applicable entry ends the walk. With no nearer plain entry the junction is exempt, by that task. With one, the junction is plain and holds only what the walk gathered below the exemption (D1; J5).
- An entry that is no gate's, that stands at `undefined`, that mixes kinds, that states `applies: true`, or that is recursive on an ancestor supplies nothing; the Validator reports each (J1; J2 and J11; J4; J6; J3).
- Then the defaults: the contributor is the task's assignee; an agent with no reviewer takes the task's assignee, and a person's junction has none.

Each field says what supplies it: `ByTask` with the task and the value's position, `ByAssignee`, or `ByDefault`. `Sources` lists the supplying tasks nearest first, as the corpus's `source` does. `Marks` gives the method's marks by key, the contributor's first: `person` or `agent`, then `reviewer` only where the reviewer differs from the contributor, or `subproject`, or `exempt`. The ruling on the self-review mark lands here and nowhere else. `Applicable` lists the gates that are not exempt, `undefined` first; `First`, `Last` and `Next` read it.

**2. The requirement's condition.** `from` defaults to the originating task's last applicable gate in its own project, and `to` to this task's first applicable gate after `undefined`. A task **stands at** its status's gate: a leaf's file, a parent's roll-up. The requirement is met when the originating task stands at or past `from`. It is due when no applicable gate of this task lies between the gate it stands at and `to`, so a task at its last gate has every requirement due. `Word` gives `met`, `unmet` or `pending`, the corpus's three words. A cross-project entry reads `Facts.Sub` of its link; `AtTrunk` says whether the same entry is met at the tip of that project's trunk, which is rule R13's question and the blockage tree's.

**3. The authorisation.** The source is **on the trunk** when its commit is on the first-parent line of the trunk's tip (D4). Off it, or with no trunk, every task is proposed and has no deciding commit. On it, the deciding commit is the nearest commit on the first-parent line, from the source back, that changes the task's file against its first parent or carries `Authorised: <id>`. A view at a tag on the line therefore reads the authorisation as it stands at the tag. The **judges** are the task's authorities as the files stand at the deciding commit, and for the root the owner as the files stand at that commit's first parent, so the owner who hands the root over is the one who accepts the hand-over (D3). The task is authorised when the author's or the committer's email is a judge's. `Way` says how: `ByMerge` when a merge brings the change in, `ByCommit` for any other change, `ByTrailer` when the commit leaves the file alone. `By` is the authority that accepts, or the author of a commit that does not. `Differs` says the task's file in view is not the one at the trunk's tip, which marks a branch's proposals.

**4. The status's date and recorder.** The deciding commit of a leaf's status is the newest commit that changes its file or carries `Reaffirmed: <id>`; its author date is the date and its author the recorder. A leaf without a file is undefined at `undefined`, dated by the newest commit that changes its task file, with no recorder: the corpus states none (F17).

**5. The review.** The commit that accepts a junction with a reviewer is the oldest one the source reaches that carries `Reviewed: <id> <gate>` and whose author or committer is the junction's reviewer as the files stand at that commit. At `defined` the authorisation stands as the review: the deciding commit accepts when the task is authorised, and no trailer counts. `Reviews` lists the reviewed junctions a leaf's status passes, each with its commit or none; a missing commit at a gate other than `defined` is what rule S11 rejects (A1). Every `Reviewed:` trailer that names a task and a gate that applies is an event with an `Effect`: `Accepts`, `Repeats`, `WrongHand` (H2), `NoReviewer` or `AtDefined`.

`Handoff` reads the next junction of a leaf when it has a reviewer. It is `Stated` when the status states the reason `review`; `Stale` when it does so after the reviewer's accepting commit (H5); and `Implied` when the status states no `review`, nothing accepts yet, and the task's newest own event is by the junction's contributor (H4). `Self` says the reviewer is the contributor, so that the Audit and the queue decide what a self-review owes.

**6. The roll-up.** A parent's status follows README.md#status step by step over its children's statuses, each a leaf's, a roll-up or a snapshot. A child whose gate gates.yaml lacks stays out; a state it lacks ranks 0. `From` names the direct child of step 3, `Considered` the children of step 1, and `Chain` follows `From` to the leaf whose file states the note. The date is the oldest among the considered children that have one.

*`4e2b` in `weather-station`.* The prototypes of 493e and 886d report the corpus at odds with the text. The owner's ruling of 2026-09-30 stands for the text, the corpus follows it since tableaux `1b0c002`, and the two now agree. `9f31` stands at function, stalled, and `c07d` at design, nominal from the firmware at its pin; both have non-zero severity, so both count. Function precedes design, and `c07d`'s exemption from reliability changes nothing, since a child enters by the gate its status names. `9f31` is the one child at function. The date is `c07d`'s 2026-09-17, the oldest. `expected.yaml` states function, stalled, blocked, 2026-09-17, from `9f31`, and the trial gives the same. The root then takes defined, nominal from `3c5d`: a stalled grandchild at a later gate does not show there, which is F14 as resolved. The status notes of 493e and 886d still say the question waits; both are stale. Cases R1 to R4 fix what the corpus has no entry for: a child exempt from early gates, and a parent exempt at the gate its roll-up takes.

**7. The events.** One commit yields, for one task, in this order: `task` when it changes the task's file; `authorised` for its trailer; `status` when it changes the status file, with the gate, state, reason and note the commit records; `reaffirmed` and `reviewed` for their trailers; `pin`. A pin event comes from a commit that changes the gitlink at a submodule path a junction or a requirement of the task names, or that changes the `commit` beside an absolute `url` in the task's file; `old` is empty when the linkage first appears. `Events(id)` adds, for each snapshot, the events of the task read there and of its descendants up to the pin, each with `Sub` set. `History` gives every task's. The order is author time; then a task's own events before a subproject's; then oldest first in the pass; then tasks in display order; then the kinds as listed.

A `status` and a `reaffirmed` event carry a `Reading`: the junction the commit is at and its model check. A commit that changes the status's gate is at the junction of the gate it records; any other is at the task's next applicable junction as the files stand at that commit (tabloio b618 decision 8). The verdict compares the commit's `Model:` trailer with the model that junction states, as an identifier or a prefix: `Match`, `Mismatch` (H3), `Missing` where the junction states a model and its contributor authors a commit with no trailer (H6), `Exempt` where `version.yaml` at that commit states a language before 0.2.1 (F24), `Unstated`, or `NoModel`. `Unread` lists the task trailers that name no task or no gate that applies (H1); they make no event.

**8. The recursive junction's status.** A leaf whose next junction is recursive keeps the gate of its own file and takes the state, reason, note, date, recorder and deciding commit from the status of the task read there: the id stated, or that project's root. `Of` is that status, a roll-up when the task is a parent, as `a500` shows in `junction-kinds`. `Own` keeps the deciding commit of the leaf's own file, where a reaffirmation is otherwise moot (F13). `Pin` gives the commit a link reads; for a submodule read from the working tree, whether the checkout has moved off the gitlink the source commit records; the tip of the subproject's trunk; and whether the commit is on that trunk's first-parent line (J13) and behind its tip.

**The past.** `At(commit)` gives the facts the files alone state as they stand at any commit of the pass: junctions, statuses, roll-ups and conditions. It follows a link, by the `url` as the project in view links it, to the subproject's own past at the commit the linkage fixes there, when that pass holds it. The history view reads the status after an event from it, and `AuthorisationAt` gives the authorisation at a commit of the trunk's line.

**Trunk, tree and roles.** `Trunk` gives the name, what names it, the ref and the tip; `How` gives the envelope's four words. `Root`, `Owner`, `Order`, `Children` and `Authorities` give the tree in display order. `Roles` gives the roles an email holds anywhere in the project, in README.md#roles's order: `owner`; `authority` for the assignee of a task with children; `assignee`; `contributor` and `reviewer` at any junction of a leaf, since a parent's junctions are defaults; `agent` beside `contributor` where the junction states a model; `observer` alone.

### Refusal

`Refused` is non-nil when the files give no structure to derive from: no `.tableaux`; a `version.yaml` that is absent, malformed or not accepted; a `gates.yaml` that is absent, whose gates do not start at `undefined` with one more at least, or hold a key that is empty, no scalar or stated twice, or whose states lack `undefined` or `complete` at severity 0, state a key twice, or state a severity that is no integer from 0; a tree with no root, two roots, a missing parent or a cycle. [`27a3/cases.md`](27a3/cases.md) lists the eighteen corpus entries it refuses and the rules that report each. Every other fault leaves the facts standing: a status at an unreviewed gate, an unknown state, a requirement on a task that is not there. The Derivation raises no diagnostic; the Validator's explain each refusal (A2).

### Deterministic

The same model and the same passes give deep-equal facts on every host: the pass prints ids in full and takes identities as committed, every list has the order stated above, and a date is the author's own. `derive` imports neither `os` nor `time`. `history` reads the repository's refs and no configuration: its command line pins the signature display, the colour, the rename detection and the date format.

### From the prototype

[`prototype/27a3`](../prototype/27a3/README.md) shows that the three riskiest facts come from a plain repository and agree with five corpus entries. The design keeps its junction walk, with the contributor and the model as one pair and the walk ending at an exemption; its trunk order; its judge of the root; and its oldest accepting review. It drops the process per lookup for the pass, the reading of every task as proposed anywhere but at the trunk's tip, the reviewer read from the files in view, and its YAML reader. Its five open points have these answers: the author or the committer judges; the oldest review accepts; the outgoing owner accepts a hand-over (D3); a view is on the trunk on its first-parent line (D4); F7 is D1.

## Conformance to the texts

The Derivation implements README.md#project (the trunk), #tasks (the tree, the authorities, the conditions), #junctions (the three kinds, the walk, the defaults, the marks, the junction a commit is at), #proposed-and-authorised-tasks, #status (the file, date and recorder, review, hand-off, roll-up), #history and #roles; SYNTAX.md#history for the events and #commit-trailers for the four trailers; and the derived facts of corpus/RULES.md. It draws no view, so no mockup binds it. Where a text is silent or two disagree, the design reads as follows.

- **F7.** README.md does not say whether a plain entry under an exemption inherits from above it. D1 says it does not.
- **Which files judge a commit.** README.md says so for the authorities and the version alone. D2 extends it.
- **The root's judge.** "The owner alone authorises the root, including a change of its assignee" names no moment. D3 takes the owner before the change.
- **Off the trunk** has no definition. D4 takes the first-parent line, as the corpus's `sensor-board` requires: W3 is reachable from `main` and reads as proposed.
- **A linked repository's trunk.** README.md resolves a name "against the local branches, then the remote-tracking branches". In a submodule's store the local branch stays where the clone leaves it. D5 reverses the order there.
- **A merge.** README.md's two commands disagree on whether a merge is an event (F11). Here a merge is an event of a file only when it changes it against every parent, and always of its trailers.
- **Trailers.** README.md's `--grep` reads any line of a message and SYNTAX.md says trailers. The Derivation reads the trailer block as Git parses it, with the keys in the case SYNTAX.md writes.
- **An `Authorised:` trailer from no authority** is a deciding commit by the text, so it returns an authorised task to proposed until an authority accepts again, where a `Reviewed:` from the wrong hand has no effect. The design follows the text ([`cases.expected.txt`](27a3/cases.expected.txt), C5).
- **The implied hand-off.** README.md's sentence for H4 does not exclude a junction the reviewer already accepted. The Derivation does (D7).
- **The third condition.** VIEWS.md lists "met, due, unmet" and the corpus writes `pending`. `Word` gives the corpus's words; `Met` and `Due` stay apart.
- **A requirement on a parent, or held by one,** reads the parent's roll-up gate; README.md speaks of "the originating task's gate" without saying so.
- **A subproject's events for a parent target** include its descendants', as "a parent's history replays its children's events" implies.
- **The working tree** and **a shallow clone** have no word in the method. The Derivation flags both and changes no fact.

## Decisions at review

1. **Fields above an exemption do not pass (F7).** A descendant that states its own entry under a not-applicable one starts from the plain default. The alternative lets its plain entry inherit from the ancestors above the exemption, so `a210` in `junction-kinds` would take the root's reviewer. Binds the corpus (`undecided: F7` goes), PLAN.md's F7, `8118`, `493e`, `886d` and `4b4f` rule 9.
2. **The files at a commit judge the commit.** The reviewer a `Reviewed:` commit must be, the junction a status commit is at and the model it states read the files at that commit, as README.md already reads the authorities and the version. The alternative reads the files in view, so a change of reviewer turns every passed gate into an S11 error. Binds `8118` (S11), `dada` (H2, H3, H6) and `8ed1`.
3. **The outgoing owner accepts a hand-over of the root.** The root's judge is the owner as the files stand before the deciding commit. The alternative reads the owner at the commit, so whoever writes their own address into the root authorises it. Binds `493e` and `dada`.
4. **On the trunk means on its first-parent line.** A source there reads authorisation from the line up to its own commit; a commit that a merge brings in reads as a proposal; a pin is on a subproject's trunk by the same test. The alternative of prototype 27a3 counts the tip alone, and a tag then shows every task proposed. Binds `4ed9` (`on_trunk`), `8118` (J13), `8ed1` and the views.
5. **A linked repository takes its trunk from the remote-tracking branch first.** In a submodule's store and in a clone a URL maps to, `refs/remotes/origin/<name>` comes before `refs/heads/<name>`; the home repository keeps README.md's order. The alternative follows README.md everywhere; the tooling plan then shows its four pins off their trunks, a J13 warning each, and reads the 42 tasks of its subprojects as proposed, with no commit at fault. README.md#project gains a sentence. Binds `8118`, `dada`, `171b` and `49ce` (A9).
6. **The Derivation refuses only what it cannot read.** A missing or unaccepted version, an unusable `gates.yaml` and a broken tree give no view data; every other error leaves the views standing beside its diagnostic. The alternative blanks every view on any error diagnostic, as tablotui `679b` A2 reads, and the tableau then vanishes while a status waits for its review. Binds `4ed9` (`data: null`), `8118`, `679b` A2, `171b` A7, tabloio `5ca9` A4 and tableaud `49ce` A6.
7. **The history implies no hand-off once the reviewer accepts.** `Implied` needs a junction nothing accepts yet, beyond README.md's sentence for H4. The alternative reports H4 whenever the contributor's event is the newest, even after the review. Binds `dada` and the corpus's H4.
