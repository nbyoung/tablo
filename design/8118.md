# Design 8118: Validator

The Validator applies the rules of the umbrella's [RULES.md](https://github.com/nbyoung/tableaux/blob/main/corpus/RULES.md) to a project the Loader read and returns diagnostics with a rule id, a severity and a position. It is two pure functions of the model: `Files`, for the 65 rules the files decide, and `Derived`, for the 11 rules that read facts the Derivation (27a3) computes. The Loader keeps its five. Five choices shape it. Every rule id has one owner, and the Validator owns every one the Loader does not, the trailer rules among them (D1). The schema library reports each failure as a leaf, and one table turns a leaf into a rule and a position; the three places where `oneOf`, `contains` and `propertyNames` give no usable leaf have a rule in code (D2). The Validator resolves which gates apply to a task itself, so it runs on a project too broken to derive (D3). The derived facts arrive as plain data, so the package imports no neighbour and its tests need no history (D4). One fault gives one error: each rule names what it silences, and a version the module does not accept silences every content rule (D5). D*n* is decision *n* under [Decisions at review](#decisions-at-review).

## The model

### Packages

| Path                | Holds                                                              | Imports                                  |
|---------------------|--------------------------------------------------------------------|------------------------------------------|
| `internal/validate` | The Validator: the two functions, the rule table, the facts it reads | `model`, `schemas`, `jsonschema/v6` and its `kind`, `yaml.v3` |
| `internal/model`    | `Diagnostic` gains two fields                                      | The standard library                     |

The package follows the pattern [4f60](4f60.md) sets: it sits under `internal/`, exports nothing from the module, and imports neither `internal/git` nor `internal/load`. It reads `yaml.v3` for one purpose, `yaml.Unmarshal` of the four embedded schema files into `any`, which amends 4f60's sentence that no other package imports the reader.

### The surface

```go
package validate

// Files applies every rule that the files alone decide. It returns the
// project's diagnostics: the Loader's, copied from p.Diagnostics, and the
// Validator's, in the order of Sort, each one once. It reads nothing, never
// fails and never panics, whatever the files hold.
func Files(p *model.Project) []model.Diagnostic

// Derived applies the rules that read derived facts: R9 from f.Requirements,
// and with f.History also R13, P5, S11, J13 and H1 to H6. It returns nil when
// f is nil, when p has no .tableaux or no gates.yaml, and when the module does
// not accept p's version. With f.History nil it applies R9 alone.
func Derived(p *model.Project, f *Facts) []model.Diagnostic

// Sort orders diagnostics as the envelope lists them: by file, a diagnostic
// with none first, then line, column, code, task, gate, commit and message.
func Sort(d []model.Diagnostic)

// Tier says what a rule needs.
type Tier int

const (
	TierLoad    Tier = iota // the Loader raises it: L1 to L4, P4
	TierFiles               // Files raises it from the model
	TierFacts               // Derived raises it from Facts.Requirements: R9
	TierHistory             // Derived raises it from Facts.History
)

// Rule is one rule of RULES.md as the module knows it.
type Rule struct {
	ID       string
	Severity model.Severity
	Tier     Tier
	Title    string // a noun phrase, as the Title column of rules.md gives it
}

// Rules holds every rule of RULES.md, in its order. RuleOf finds one by id.
var Rules []Rule
func RuleOf(id string) (Rule, bool)
```

`model.Diagnostic` gains `Commit string`, the commit a finding concerns, in full, and `Trailer string`, the trailer line it concerns as `Key: value`. The Plumbing command's diagnostic already carries both ([4ed9](4ed9.md), "The envelope"), and the Loader sets neither.

### One owner for each rule

| Owner                | Rules                                                                                           | Count |
|----------------------|-------------------------------------------------------------------------------------------------|------:|
| The Loader           | L1 to L4, P4                                                                                    | 5     |
| `validate.Files`     | P1 to P3; G1 to G12; T1 to T12; R1 to R8, R10 to R12; J1 to J12, J14 to J17; S1 to S10, S12      | 65    |
| `validate.Derived`, with or without a history | R9                                                                     | 1     |
| `validate.Derived`, with a history | P5, S11, J13, R13, H1 to H6                                                       | 10    |

No rule has two owners: `Files` copies the Loader's diagnostics through and raises none of its codes, and test T1 holds the table to RULES.md. [`rules.md`](8118/rules.md) gives each rule one row. **One rule, one function, one id**: a rule in code is one method of the run named by its id, `s7`, `t10`, `h4`, which returns whether the rules after it stop; a rule the schema decides is its rows in [`schema.md`](8118/schema.md) and has no function; G10, J4, S5, S6, R6 and R7 have both, for the part a schema cannot see. `Diagnostic.Code` is the rule id and nothing else.

The line between a rule and a derived fact is the id. A finding with an id in RULES.md is a diagnostic and the Validator raises it; a disagreement with no id, a proposed task or a stale status, is the Audit's (dada), which adds the action and the resolver to both. The Derivation computes facts and raises nothing.

### What `Files` does, in order

1. `!p.Exists`: P1, and nothing else.
2. `version.yaml`: P2 when the file is absent, else its schema (P3). When the Loader raised P4 the run ends here: schemas of this language version misjudge a file written for another (D5).
3. `gates.yaml`: G1 when absent, else its schema and G6, G9, G10, G12.
4. The tree: T8, then per task T1, T9, T10, then T12 per parent.
5. Each task file in id order: its schema, T7, the junction rules, the requirement rules, J12.
6. R2, over the requirement edges step 5 keeps.
7. Each status file in id order: S1, S2, its schema, S5 to S10 and S12.

**The structure the rules share** is one unexported value per project, built once per run and for each linked project a rule reads:

```go
// shape is what the rules ask of a project beyond its files.
type shape struct {
	gates    []string            // the scalar gate keys, in file order, the first statement of each
	gate     map[string]int      // a key to its index in gates
	states   map[string]bool
	reasons  map[string]bool
	unread   map[string]bool     // ids whose task file is in p.Files and gave no task: L1
	children map[string][]string // by the parent id as written
	roots    []string            // tasks with a nil Parent, in id order
}

// ancestors returns the tasks above id, nearest first, and whether the chain
// is whole: it ends at a task with no parent and meets no task that is
// missing, unread or already met.
func (s *shape) ancestors(id string) (chain []string, whole bool)

// kindAt resolves the kind of a task's junction at a gate: plain at
// undefined; else the first entry at that key that decides, from the task's
// own and then its ancestors', nearest first; else plain.
func (s *shape) kindAt(id, gate string) resolved // plain, recursive, notApplicable

// applicable returns the gates that apply to a task, in order.
func (s *shape) applicable(id string) []string
```

An entry **decides** when it is a mapping of one kind and well formed as that kind: a plain entry; `{ applies: false }` and no other field; a recursive entry on the task itself, never on an ancestor. Any other entry, `applies: true` or a `Mixed` one, decides nothing, and the walk goes on to the next ancestor. So an entry that a J rule rejects causes no second finding about the gate it meant to change. This is the corpus's reference reading, `resolve_kind` in `check.py`.

**A partly read project** follows the method's rule for reading (SYNTAX.md "Layout", RULES.md "Reading a file"). From a file that L2 or L3 rejects the Loader gives the first statement of each key and the first document, and every rule runs on that. A task file that L1 rejects gives no task: its id is **unread**. T9, R1, S1 and H1 stay silent about an unread id, T8 does not count roots while any task is unread, and a chain that reaches an unread task is not whole, so S11, H4 and H5 skip the leaf below it. A status file that L1 rejects gives no status, and its leaf reads as one with no file. With no `gates.yaml` every rule that names a gate, but J2, J11 and the key pattern of J1, stays silent.

### The schemas

The Validator compiles the four embedded schemas once, with `AssertFormat`, so that `format: email` and `format: uri-reference` assert as SYNTAX.md intends; draft 2020-12 leaves them annotations by default. It validates `File.Root.Plain()` of each file that gave a model and walks the error tree to its leaves. [`schema.md`](8118/schema.md) is the whole mapping: a leaf's instance location and keyword location give the rule and the gate; `File.Root.At` of the instance location gives the node and so the position; the leaf's kind gives the message, in the Validator's own words. An unknown field reports at its key through `Field.KeyPos`, and a missing field at the mapping that lacks it.

Three leaves are useless, and code replaces each. `propertyNames` reports a junction key with no location, so J1, J2 and J11 read `Junction.Gate` and `KeyPos`. `contains` gives one leaf per state for one absent state, so G12 reads the states. The junction's `oneOf` gives the leaves of all three kinds, so the whole-file run drops every leaf under `junctions/<gate>`, and each entry validates alone against the schema of the kind `Junction.Kind()` names, compiled by its pointer, `task.schema.yaml#/$defs/plain`. The requirement's `oneOf` stays in the table, since its two leaves name the one fault.

The schema stays the judge: every file the schema rejects has at least one error diagnostic, which test T5 proves by mutation. Prototype 8118 asked whether to tag the rules in the schemas or to check in code with the schema as a gate; the table is neither, and it leaves the schema files byte-equal to SYNTAX.md's.

### Positions, fields and messages

A diagnostic's position is the node at fault. A finding about a file as a whole (P2, G1, T1, T12, J12, S1, S2, P5, H4) carries the file and no line; a finding about the project or a commit (P1, T8, H1, H2, H3, H6) carries no file. `Task` is the id of the task or status file the finding sits in, whatever the name is, so T1 reports `leaf-two`; `Gate` is the key a rule names, as written, so G5 reports `Design`. T12 sits in the parent's file and names the parent, as the corpus states it.

A message is a fixed format per rule or per leaf kind, filled from the files. It holds no line, no column, no absolute path and no text of the schema library, whose wording follows Go's map order where a mapping has two unknown fields. Two runs give equal bytes, and tabloio's write commands compare a message across two trees (`b618`, step 8).

### The derived facts

`Derived` reads plain data. The Derivation fills it, through the adapter in the Plumbing command's `snapshot.go`; a test writes it as a literal.

```go
// Facts are the derived facts that the rules beyond the files read.
type Facts struct {
	Requirements []Condition           // one for each requires entry the Derivation resolves
	Junctions    map[Junction]Resolved // each task's junction at each gate that applies to it
	History      *History              // nil when the source has no commit
}

// Junction names the meeting of a task and a gate.
type Junction struct{ Task, Gate string }

// Resolved is a junction after inheritance and the defaults.
type Resolved struct {
	Recursive                    bool
	Contributor, Model, Reviewer string // a plain junction; Reviewer is "" where it has none
}

// Condition is the derived condition of one requires entry.
type Condition struct {
	Task     string // the terminating task
	Index    int    // the entry's index in Task.Requires
	Origin   string // the originating task's id
	From, To string // the two gates, resolved
	Stands   string // the gate the originating task stands at
	Met, Due bool
	MetAtTip bool   // a cross-project entry that the tip of the originating project's trunk meets
}

// History is what one pass over the history of the source gives.
type History struct {
	Trunk    string   // the trunk's name; "" when it is undetermined
	Commits  []Commit // every commit with a method trailer, an event or a junction, newest first
	OffTrunk []Pin    // each linkage whose commit its subproject's trunk does not contain
}

// Commit is one commit of the history in view.
type Commit struct {
	Hash              string     // in full
	Author, Committer string     // the two emails
	Tableaux          string     // the language version.yaml states at the commit; "" when none
	Trailers          []Trailer  // Authorised, Reviewed, Reaffirmed and Model, in message order
	Events            []Event    // the events of the history view that the commit gives
	At                []Junction // the junctions the commit is at, as README.md "Junctions" defines it
}

type Trailer struct{ Key, Value string }    // "Reviewed", "9f31 design"
type Event struct{ Task, Kind, Gate string } // Kind as the history schema's event enum

// Pin is a linkage whose commit is off its subproject's trunk.
type Pin struct {
	Task  string
	Gate  string // the junction's gate; "" on a requirement
	Index int    // the requirement's index; -1 on a junction
	Trunk string // the subproject's trunk
}
```

**Without a history.** A tree, as `git write-tree` gives a pre-commit hook, and an unborn branch have no commit (`Location.Commit` is empty). The Derivation then leaves `History` nil and `Derived` skips ten rules: P5, S11, J13, R13 and H1 to H6. R9 needs the statuses and no history, so it runs whenever `Requirements` is filled. `Files` never needs a history. `Derived` trusts nothing in the facts: a task, an index or a gate the project lacks skips its row.

Each of the ten is a few lines over these primitives, and [`rules.md`](8118/rules.md) states each. Three readings shape them. A commit is **by the reviewer** when its author or its committer is, as README.md states for a review, and S11 and H5 find the review themselves from `Trailers`; a commit is **by the contributor** when its author is, as an event's actor is its author (D8). S11 exempts the gate `defined` whatever the task's authorisation, as RULES.md writes it (D7). H2 stays silent at a junction with no reviewer, where the corpus entry `junction-kinds` holds such a trailer and states no finding (D10), and H4 reads the newest event as README.md words it (D9).

### Subprojects

The Loader links each `subproject` field to a `*model.Link` and reads the project behind it. The Validator applies no rule to a linked project's files and copies none of its diagnostics: a subproject's faults are findings of its own `validate` run, in its own repository or with `-C <dir>` in a monorepo, where a path below its own `.tableaux` means something. From a linked project the Validator reads four things, each reported at the `subproject` field of the file that names it: whether it resolves (J8, from `Link.Problem`, and from a version the module does not accept); whether the task exists there (J9, the `id` or the one root); which gate `from` names and whether it applies to the originating task, through that project's own `shape` (R6); and whether a junction and a requirement of one task read one task (R12, by the identity of the `*Link` the Loader shares). J15, J16 and J17 read `Link.Form`, `Link.Commit` and the field as written; J14 is the schema's. The six rules apply alike to a junction's `subproject`, with the gate, and to a requirement's, without.

### Errors, and what is deterministic

Neither function returns an error or reads a file, Git, the environment or the clock. The same project and the same facts give equal slices; every map the code ranges over is sorted first. Both are safe for concurrent use, since the compiled schemas are immutable and the run holds its own state.

### From the prototype

[`prototype/8118`](../prototype/8118/README.md) shows that the embedded schemas run unchanged and that a schema failure finds a line and a column; the design keeps both, and its order of checks for the tree and the requirements. It drops the prototype's YAML reader and its schema validator for the two modules the README names, its `parse` code for L1, its T8 position at the second root's file for a finding with no file, and its hand filter for the status cascade for a row of the table. Its four findings have these answers: the two dependencies, as the owner decided at the function gate; the table of [`schema.md`](8118/schema.md); an id is its source text at the four places, as the Loader built it, and T7 warns of every unquoted one (D6); a project-level finding has no file. Run against the built corpus today the prototype agrees with 52 entries and differs on 49. The design's files tier covers 36 of those 49 whole, and the other 13 each need a derived fact: `handoff-inferred`, `handoff-stale`, `junction-kinds`, `model-mismatch`, `model-trailer-missing`, `requires-commit-behind`, `review-by-non-reviewer`, `status-unreviewed-gate`, `subproject-pin-off-trunk`, `trunk-undetermined`, `unknown-trailer`, `unmet-requirement` and `weather-station`.

## Conformance to the texts

The Validator implements RULES.md row by row; [`rules.md`](8118/rules.md) keeps its ids, severities and entries and adds what the implementer needs. It follows SYNTAX.md "Layout" for what a tool reads from a file that L1, L2 or L3 rejects, the four schemas of SYNTAX.md as `schemas/` embeds them, README.md "Tasks", "Junctions" and "Status" for the tree, the requirement and the status rules, and README.md "Junctions" for the junction a commit is at. It builds no view. Every rule has a corpus entry. The texts are silent, or disagree, in these places:

- **G7.** RULES.md cites `states: minItems: 1`; the schema says 2. The schema decides, so one state alone is G7.
- **J7 and T6.** J7's row covers "`id`, when present, is an id", which T6 also covers. A malformed `subproject.id` is T6, as `check.py` reads it, and J7 keeps the shape of the field.
- **P1.** RULES.md still says "at the root of the repository"; SYNTAX.md and the Loader take the nearest `.tableaux`, and P1 follows `Project.Exists`.
- **S9 and S10 at `undefined`.** A status at `undefined` states the state `undefined` by S4, whatever the next junction is; S9 and S10 start at the gate after.
- **R2.** The text does not say where a cycle reports. Each requirement on a cycle reports at its `id`.
- **S11 and a proposed task.** README.md lets the authorisation stand as the review of `defined`; it does not say what holds while the task is proposed (D7).
- **H2, H4 and H6.** README.md does not say whether a wrong-hand review at a junction with no reviewer is reported, which events count as the newest, or whether "by its contributor" reads the author or the committer (D8, D9, D10).
- **The audit mockup.** `docs/mockups/audit.md` draws H3 at `defined` for commits that edit a task file. README.md now puts a commit at a junction only when it changes a status or reaffirms one (tabloio `b618`, decision 8), so such a commit is at none. The mockup stays as drawn.
- **Entries with no corpus fixture.** The corpus exercises every rule and not every branch: an unquoted id that YAML reads as a string (T7); J8, J9 and J14 to J17 on a requirement's `subproject`; R6 across projects; a `Reviewed:` gate that does not apply (H1); a subproject at a version the tool does not accept (J8). Tests T7, T11 and T13 build these.
