# Design 493e: Structural views

This task gives four views as data: the gate definition, the task definition, the authority delegation and the task assignment. It also fixes, once, what the three view tasks share, so that `886d` and `8ed1` add views and repeat no decision. Six choices shape it (D*n* is decision *n* under [Decisions at review](#decisions-at-review)). The data types live in a public package, `view`, and the functions that fill them in `internal/views`, over `*derive.Facts` (D1). A view's data is one flat object whose keys are the tags tabloio's renderers already read; a level the data does not reach leaves its keys out (D2). Every view carries the legend and repeats nothing the envelope states (D3). The views select, count and word, and derive nothing: every field names the method of the Derivation that gives it, and the one fact no method gives becomes one method more there (D4). Where a front end expects worded text or two front ends expect two shapes, the data carries the facts and one adapter pays (D5, D6). The three points VIEWS.md leaves open take one rule each: the assignment counts, a person's models, and the authority view's selection (D7 to D9).

## The model

### Packages

| Path                              | Holds                                                                                                  | Imports                              |
|-----------------------------------|--------------------------------------------------------------------------------------------------------|--------------------------------------|
| `github.com/nbyoung/tablo/view`   | The data of every view: exported types with JSON tags, no function and no method                       | Nothing                              |
| `internal/views`                  | One function per view, `Gates`, `Task`, `Authority`, `Assignment`, and the builders of the shared types | `view`, `derive`, `history`, `model` |
| `internal/derive`                 | One method more, `Facts.LastChange`                                                                    | As today                             |

The types are public because two front ends name them: tableaud's adapters take "tablo's type" for each view (438a, "Adapters") and tabloio's Read commands ask for "an exported Go type" (5ca9 A3). They stay out of the root package, where forty types of data would bury the API. A front end that keeps types of its own, as tabloio and tablotui do, marshals `Envelope.Data` and decodes it, and imports nothing new.

The functions take `*derive.Facts` and a `views.Query`, not the `*Snapshot` and `Params` of 4ed9's `deriver`: `snapshot.go` does not stand yet, and `internal/views` cannot import the root package that imports it. `snapshot.go` wraps each function in one line ([`model.md`](493e/model.md#internalviews-the-functions)). A view function fails in no case. Its caller guarantees two things, and `Snapshot.View` already owes both: the Derivation does not refuse the project (`data` is then null, 27a3 decision 6), and the task the query names is one of the project (else a `*NotFoundError`). An email that holds no position is no error: the lists are empty (49ce A4).

The three view tasks share both packages. `886d` adds `view/tableau.go`, `view/queue.go`, `view/blockage.go` and their files in `internal/views`; it calls the builders and extends `Query`.

### How a level nests

A view's struct holds its glance fields and embeds a pointer to its detail struct and a pointer to its provenance struct. `encoding/json` writes the fields of an embedded struct as keys of the outer object and skips a nil embedded pointer, so:

- the JSON is one flat object at every level, and the keys of glance never move;
- at the resolved level and below, every key is present: a list is an array, `[]` when empty; an absent object is `null`; an absent text is `""`;
- above the resolved level, the keys are absent. A consumer tells "no references" from "not asked" without reading `params.level`.

Two keys nest a level inside a list item by the same means: `junctions[].from`, tagged `omitzero` and nil where the view shows no suppliers, and `sections[].positions` of the assignment. The envelope states the level; the data does not repeat it.

[`model.md`](493e/model.md#view-what-every-view-shares) declares the shared types and names, field by field, the method that fills each. In summary:

| `Supplier`, `Stated`     | What supplies one field of a junction: a task with file, line and column, `assignee`, or `default` | `Field.By`, `.Task`, `.Node`                       |
| `SubRef`                 | The task a link reads: `url`, `id`, `task`, `form`, `commit`, `why`                       | `Snapshot`, `model.Link`                                    |
| `Status`, `Origin`       | A status with its `kind` and, for a roll-up or a snapshot, where it comes `from`          | `Status`, `Status.Derived`                                  |

A path in the data is relative to the project directory and starts `.tableaux/`, as a diagnostic's does; the `files` of a commit fact alone are relative to the repository root, as Git names them. A command line names commits in full and paths from the repository root. With no history, every commit is null and every list of commands is empty.

### The gate definition

`Gates(f, q)`; type `view.Gates`. `q.Task` is the task parameter, `""` for none. The view takes no person.

| Level      | Key        | Holds                                                                                               | From                                                         |
|------------|------------|-----------------------------------------------------------------------------------------------------|--------------------------------------------------------------|
| glance     | `legend`   | The legend                                                                                          | As shared                                                    |
| glance     | `task`     | The task parameter as a `TaskRef`, or null                                                          | The model                                                    |
| detail     | `for_task` | With a task: one item per gate of `Facts.Gates()`, `undefined` first: `gate`, `applies`, `references`, `stated_by`. Without: `[]` | `Junction(task, gate)`: `applies` is `Kind != NotApplicable`, true at `undefined`; `References`; `ReferencesFrom` |
| provenance | `files`    | `.tableaux/gates.yaml`, then `.tableaux/version.yaml`, each with the newest commit that changes it, or null | `LastChange("gates.yaml")`, `LastChange("version.yaml")` (D4) |
| provenance | `commands` | Four lines, in this order, `<c>` the source commit and `<p>` the path of each file from the repository root: `git show <c>:<p>` for each file, then `git log -1 --format='%H %as %an <%ae> / %cn <%ce> %s' <c> -- <p>` for each | `Facts.Log().Source`, `.Dir` |

The gate definition shows part of the legend at glance and all of it at detail; the data holds it whole at both, as every view's does. The language version and the trunk stand in the envelope, as `project.tableaux` and `source.trunk`, and the data repeats neither.

`Task(f, q)`; type `view.Task`. `q.Task` is required. `q.Person` sets `acts` on the junctions and selects nothing; a front end marks the assignee and the authorities by comparing emails.

| Level      | Key                     | Holds                                                                                | From                                                          |
|------------|-------------------------|--------------------------------------------------------------------------------------|---------------------------------------------------------------|
| glance     | `legend`, `task`, `assignee` | The legend, the task, its assignee                                              | The model                                                     |
| glance     | `parent`                | The parent with the task's `order`, null for the root; `order` is null when the file states none | `Authorities(id)[0].Task`; the model's `Parent.Order`  |
| glance     | `status`                | The status, with `from` for a roll-up or a snapshot                                  | `Status(id)`                                                  |
| glance     | `authorised`            | Whether the task is authorised (438a decision 9 shows a proposal at glance)          | `Authorisation(id).Authorised`                                |
| detail     | `description`, `references` | As the file states them                                                          | The model                                                     |
| detail     | `path`, `siblings`      | The ancestors from the root with the task last; the number of the parent's children, 0 for the root | `Authorities(id)` reversed; `Children(parent)`    |
| detail     | `children`              | Each child with its `order` and status, in display order                             | `Children(id)`, `Status(child)`                               |
| detail     | `authorities`           | One item per ancestor, nearest first: `email`, `by`                                  | `Authorities(id)`                                             |

| provenance | `sources`               | The suppliers of every junction, by gate, then field                                 | `Field.By`, `.Task`, `.Node`; `Junction.Entry`, `.ReferencesFrom` |
| provenance | `status_commit`         | The deciding commit of the status: the `Commit` of the last status of `Chain(id)`, so a roll-up shows its leaf's | `Chain(id)`                        |
| provenance | `own_commit`            | For a snapshot, the deciding commit of the task's own file; else null                | `Status.Own`                                                  |
| provenance | `authorisation`         | `commit`, `way`, `by`, `email`, `judges`, `why`, `differs_from_trunk`, `uncommitted` | `Authorisation(id)`: `Commit`, `Way`, `Author` and `Committer`, `By`, `Judges`, `Why`, `Differs`, `Uncommitted` |
| provenance | `considered`, `chain`   | The children a roll-up considers, `[]` for a leaf; the statuses the status comes through | `Status.Considered`; `Chain(id)`                          |
| provenance | `linkages`              | One per snapshot of the task: the gates, the `SubRef`, where the entry states the url, the `commit` field as written, the pin's place on the subproject's trunk, the pinned commit, and the commit of the newest pin event of the link | `Snapshots(id)`; `Pin(link)`; `Snapshot.Facts.Trunk()`, `.Log().Commit(pin)`; `Events(id)` |

An event row holds `date`, `commit`, `by` (the author's email) and `kind`; `recorded` for a status event, with the gate, state, reason and note as the commit records them; `gate` for a reviewed event; `pin` for a pin event; and `subproject`, with `url` and `task`, for an event the Derivation takes from a subproject. The history view's line is `8ed1`'s.

### The authority delegation

`Authority(f, q)`; type `view.Delegation`. The tasks **in view** start as the subtree under `q.Task`, in display order. `depth` is 0 for the task the view starts at.

1. With `q.Person`, a task stays when the person is its assignee or one of `Authorities(id)`; then every ancestor of a kept task, within the subtree, joins. This is "the subtrees the person has authority over, and the chain above the person's tasks" (D9).
2. With `q.Proposed`, of the tasks rule 1 leaves, the proposed stay; then their ancestors within the subtree join, each with `proposed` as it stands, so the tree stays a tree (c48a A4, e2b6 A6).
3. No level hides a row (c48a A1). An email that holds nothing, or a tree with no proposal, gives `rows: []`.

| Level      | Key         | Holds                                                                                       | From                                                           |
|------------|-------------|---------------------------------------------------------------------------------------------|----------------------------------------------------------------|
| glance     | `legend`, `rows` | Per task in view: `id`, `title`, `depth`, `assignee`, `parent`, `delegated`, `proposed`, `differs_from_trunk`, `uncommitted` | `Children`, `Leaf`, the model's assignees; `Authorisation(id)`: `Authorised`, `Differs`, `Uncommitted`. `delegated` is false for the root of the project |
| detail     | `parents`   | Per row with children: `assignee`; `authorities`, the chain its children have; `children`, every child id; `defaults`, the parent's resolved `Junction` at each gate where its own file states an entry, in gate order, with `from`; `sources`, their suppliers | `Authorities(first child)`; `Children`; the model's `Task.Junctions` for the gates; `Junction(parent, gate)` |
| provenance | `deciding`  | The deciding commits of the rows, grouped by commit, way and hand: `commit`, `way`, `merged`, `by`, `email`, `tasks`. Newest first by the commit's place in the pass; then `change`, `merge`, `trailer`; tasks in display order | `Authorisation(id)`: `Commit`, `Way`, `Author`, `Committer`, `By`; `merged` is `Commit.Parents[1]` of a merge |
| provenance | `undecided` | The rows with no deciding commit, grouped by reason, in the order the reasons first occur   | `Authorisation(id).Why`                                        |
| provenance | `commands`  | One line when the trunk has a tip: `git log --first-parent --format='%H %as %ae %ce %P' <trunk tip> -- <dir>/.tableaux/tasks` | `Facts.Log().Trunk.Tip`, `.Dir` |

A default is resolved, with its marks and the supplier of each field, because the Derivation gives marks for a resolved junction and for nothing else (D5). Off the trunk every row reads `proposed`, `deciding` is empty and `undecided` holds one group, `off_trunk`.

### The task assignment

`Assignment(f, q)`; type `view.Assignment`. The tasks in view are the subtree under `q.Task`. A **position** is an assignment, a contribution or a review. Contributions and reviews count on leaves alone, since a parent's junctions are defaults; an assignment counts on every task (D7).

- **The emails**, in this order: the assignees of the tasks in view, in display order; then every other contributor and reviewer of a plain junction of a leaf in view, by task in display order, then gate, the contributor before the reviewer. With `q.Person`, that email alone; an email with no position gives `people: []`.
- **Next.** A leaf's next gate is `Next(id, Status(id).Gate)`; a leaf at its last gate has none. A junction is next when its `stands` is `next`.
- **Contributes, reviews.** The plain junctions of the leaves in view at which the email is `Contributor.V`, respectively `Reviewer.V`, in gate order, then display order. A junction the email both contributes to and reviews stands in both lists: the position is a fact of the plan, and the queue decides what a self-review owes (27a3, `Handoff.Self`).

| Level      | Key            | Holds                                                                                              |
|------------|----------------|----------------------------------------------------------------------------------------------------|
| glance     | `legend`, `people` | Per email: `email`; `owner`, the email is `Facts.Owner()`; `assigned`, the number of tasks in view whose assignee it is, parents among them; `contributes_next` and `reviews_next`, the next junctions of each list; `models`, the distinct `Model.V` of its contributions at every gate, in the order of the list (D8) |
| glance     | `recursive`    | The leaves in view whose next junction is recursive, in display order: nobody in this project contributes there |
| detail     | `sections`     | Per row of `people`, in its order: the eight lists below                                           |
| detail     | `assigned`     | Per task assigned: the task, `under` (the parent's id), its status, and for a leaf with a next gate `next_gate` and `next`, the `Junction` there |
| detail     | `recursive`    | Per assigned leaf whose next junction is recursive: the task, the gate, the `SubRef`, and the status of the task read there, from `Snapshot.Facts` |
| detail     | `contributes`, `reviews` | The two lists, each row the task and the `Junction`                                      |
| detail     | `models`       | The contributions that state a model, grouped by gate, model and `Model.Task`, in gate order, then first occurrence: `gate`, `model`, `stated_by`, `junctions`, `next` |
| detail     | `counts`       | Per gate of `Facts.Gates()`, `undefined` first: `standing`, the tasks assigned whose status names the gate, a parent by its roll-up; `contributes`, `contributes_next`, `reviews`, `reviews_next` |
| detail     | `authority`    | Per assigned task with children and no ancestor assigned to the same email, in display order: the task and the number of its descendants |
| provenance | `sections[].positions` | The positions grouped by source, in this order: one `assignee` row with every assigned task, `from` being `by: own`, `key: assignee`, since each task's own file states it; one `authority` row per item of `authority`, `from` naming the `assignee` key of that task's file; the `contributes` rows grouped by gate, `from` (the contributor's `Stated`), `reviewer` and `reviewer_from`; the `reviews` rows grouped by gate, `reviewer_from` and `from`; one `recursive` row per item of `recursive`, with `url`, `pin` and `from` naming the entry. Within a kind, gate order, then first occurrence |

Every count is a count of a list the data holds: `contributes_next` is the number of rows of `contributes` that stand `next`, and the counts by gate sum to the lists. The view carries no commit and no command: VIEWS.md asks, per position, for "the file and the ancestor that states it, or the plain default", and `Stated` holds the file, the key, the line and the column.

### Deterministic

`view` holds data alone. `internal/views` runs no process and reads no file, clock or environment: it calls `time.Unix` and `Format` to write an author time and nothing else of `time`. Every list has the order stated above, which is the Derivation's or the model's file order. The same facts and the same query give deep-equal values, so the same repository and parameters give the same bytes (4ed9, "Determinism").

### The schema and the golden data

The data has no schema file of its own: [`493e/data.schema.yaml`](493e/data.schema.yaml) joins `envelope.schema.yaml`, so that one file, the embedded `tablo.EnvelopeSchema`, states schema `tablo/1` whole and 4ed9's T6 covers the data of every envelope a test produces (D11). Each view task appends its `$defs`, under the prefix `view_`, and its entries to `allOf`: the data object per command, and the keys each level requires and forbids. The lists of words stay in [`model.md`](493e/model.md#view-what-every-view-shares) and in the Go comments; the schema types them as strings.

The golden data lives in `internal/views/testdata/<entry>/<command>[-<focus>].<level>.json`: the `data` object alone, encoded as `Envelope.JSON` encodes it. [`493e/golden/`](493e/golden/) holds the first five. ### Kept and dropped

From [`prototype/493e`](../prototype/493e/README.md) the design keeps the four views as functions of one set of facts, the tree rows of the authority view, the people rows of the assignment, and the three words `met`, `unmet`, `pending`. It drops the keys `glance`, `detail` and `provenance` as objects, for one flat object; `view`, `ref`, `on_trunk` and `params` in the data, which the envelope states; `-window` and `-columns` and the gate view's `folded`; every loader and derivation it carries, for `internal/derive`; and the mixed supplier field `default`, a task id or `assignee`, for `Stated`. Its open points have these answers:

| Q4 and the marks                          | Settled: five marks, 🧑 among them (F23), and 👀 only where the reviewer differs from the contributor; `Junction.Marks` gives them |
| Requirement condition                     | Settled by 27a3: met when the originating task stands at or past `from`; the third word is `pending`              |
| Assignment counts                         | Open in the text: D7                                                                                            |
| A person's models                         | Open in the text: D8                                                                                            |
| Authority of a person, and `proposed`     | Open in the text: D9                                                                                            |

## Conformance to the texts

The design implements four sections of [VIEWS.md](https://github.com/nbyoung/tableaux/blob/main/VIEWS.md): "Gate definition", "Task definition", "Authority delegation" and "Task assignment", each level by the rows of its table above, and of "What every view shares" the data table, the person and task parameters and the three levels. The marks follow README.md#junctions through `Junction.Marks`, the self-review ruling with them. The role-based level and the person default stay in 4ed9; this task receives a resolved level. Where a text is silent, or two disagree:

- **The assignment counts, a person's models, the authority view's `person` and `proposed`.** VIEWS.md states none of the three to the point of a rule. D7 to D9.
- **A junction at `undefined`.** README.md#junctions says every task has a junction at every gate, and that `undefined` has no work of its own; the Derivation resolves none there. `junctions` starts after `undefined`, and `for_task` and `counts`, which list gates, start at it.
- **"The newest events"** of the task definition names no number. The data holds five, and the count of all.
- **The provenance of a position.** VIEWS.md asks for the file and the ancestor. `assignment.md` also prints the commit that last changed the line; no fact gives a commit per line, and the data carries the line (D10).
- **The mockups stay as drawn.** `gates.md` prints the language version and the trunk in the view; here they stand in the envelope. `assignment.md` counts from 📝; `counts` starts at `undefined`, as c48a decision 4 chose. `authority.md` folds a parent of ten; the data holds every row and a front end folds.
- **The VIEWS.md example of the assignment** gives the agent no review at a next junction, and `assignment.md` gives it two. By D7 an email reviews wherever it is the junction's reviewer, its own work included.

## Decisions at review

1. **A public package `view` for the data, and `internal/views` for the functions.** A front end may import `github.com/nbyoung/tablo/view` beside the root package, which amends 4ed9's "the root package and nothing else". The alternative puts the types in the root package: one import, and forty more names beside `Open`, `Snapshot` and `Envelope`. Binds `4ed9`, `886d`, `8ed1`, `dada`, tableaud's adapters. Accepted by the owner on 2026-10-07, as stated.
2. **One flat object; a level the data does not reach leaves its keys out.** The keys are tabloio's tags, so two built front ends read the data as they read their fixtures. The alternatives: the prototype's three nested objects, which no built front end reads; or every key always present, where an empty list cannot say "not asked". Binds `886d`, `8ed1`, `dada`, `4b4f` and the three front ends. Accepted by the owner on 2026-10-07, as stated.
3. **Every view carries the legend, whole, at every level, and nothing else of the envelope.** A rendering then stands alone, as tabloio's and tablotui's types expect, and tableaud needs no second call. The gate definition therefore holds criteria at glance. The alternative keeps the legend in `gates` alone and has every front end call twice. Binds `886d`, `8ed1`, `dada`; amends `e3ed` A2 and `0afa` A3 for `level`, `project`, `ref` and `params`. Accepted by the owner on 2026-10-07, as stated.
4. **The Derivation gains `Facts.LastChange`.** The gate definition's provenance needs the newest commit that changes `gates.yaml` and `version.yaml`, and no method gives it. The method is three lines over what the Derivation already indexes. The alternative has the view scan `Facts.Log()` itself, which is a derivation outside the Derivation. Binds `27a3`. Accepted by the owner on 2026-10-07, as stated; the method joins the surface of `27a3` after its implementation review, and its design records it.
5. **tablo emits facts, never sentences, and one shape per fact.** A roll-up's steps are `considered` and `chain`, and a linkage is a typed object, where tabloio's `e3ed` A9 reads worded pairs; a parent's default is the shared resolved `Junction`, where tableaud's `e2b6` A4 reads the unresolved entry and tabloio's `c48a` A2 three `_from` keys; a junction's place is `stands` in every view, where `c48a` A3 reads `when`. tabloio's builders and tableaud's adapters pay, and tablo stays free of English. The alternative keeps each key as its front end first wrote it, and tablo then words prose for one renderer. Accepted by the owner on 2026-10-07, as stated.
6. **The words.** A deciding commit accepts by `change`, `merge` or `trailer`; a model reads `agrees`, `differs`, `missing`, `exempt` or `unstated`; the third junction kind is `not_applicable`, as the corpus and the model spell it (27a3 leaves the word to this task); a status's kind is `recorded`, `absent`, `rollup` or `snapshot`; an undetermined fact gives its reason with underscores. The alternative for the first two is the Derivation's own `commit`, `match` and `mismatch`, which no front end expects. Binds `b618` A4, which wrote `not-applicable`. Accepted by the owner on 2026-10-07, as stated.
7. **The assignment counts.** An assignment counts on every task, parents among them; a contribution and a review count on leaves alone; a junction is next when it stands at the leaf's next applicable gate; a self-review stands in both lists. VIEWS.md's example (10 and 27 assigned) fits; the text states none of it. The alternative counts a parent's default junctions as positions, which counts the same work at every level of the tree. Accepted by the owner on 2026-10-07, as stated. VIEWS.md states the four rules under "Task assignment" from that day, and its example follows the approved mockup: the owner reviews 26 next junctions and the agent 2, its own work.
8. **A person's models** are the distinct models of the junctions the email contributes at, at every gate, in gate order. The alternative lists the models of the next junctions alone, and an agent's row then changes with every status. Accepted by the owner on 2026-10-07, as stated. VIEWS.md's example takes the order this rule gives, `claude-haiku`, `claude-opus`, `claude-fable`, `claude-sonnet`, as the approved mockup draws it.
9. **The authority view's selection.** `person` keeps the person's own tasks, the tasks under them, and the ancestors of both within the view; `proposed` then keeps, of those, the proposed tasks and their ancestors. The alternative for `proposed` drops the ancestors, as the prototype does, and a front end then draws a forest. Binds `c48a` A4, `e2b6` A6. Accepted by the owner on 2026-10-07, as stated. VIEWS.md says from that day that the filter keeps the ancestors of the proposed tasks.
10. **No commit per line, and no committer time.** A position's provenance is the file, the key, the line and the column; the commit fact carries the author time alone. The Derivation's pass keeps neither a blame nor the committer's time. The alternative adds both to `internal/history`: a second date per commit, and one `git blame` per file. Binds `c48a` A3, `e3ed` A8, and `8ed1`, whose history line prints the committer. Accepted by the owner on 2026-10-07, as stated; `8ed1` may reopen the committer's time for the history line.
11. **The data's schema joins `envelope.schema.yaml`; the golden data lives in `internal/views/testdata/`.** One file states `tablo/1`. The alternative is one schema file per view beside the envelope's, which a consumer must find and join itself. Binds `4ed9` (T6), `886d`, `8ed1`, `dada`. Accepted by the owner on 2026-10-07, with one amendment: the schema types the closed sets of words of decision 6 as `enum`, not as strings, so [`493e/data.schema.yaml`](493e/data.schema.yaml) gains an `enum` for the way a deciding commit accepts, a model's reading, the junction kind, the status kind and the reason a fact is undetermined, and the sentence above that leaves the lists of words to `model.md` no longer holds for those sets. A word added to a set widens `tablo/1` and changes no meaning.
